# Huawei catalogue

The catalogue has two parts, both generated by `tools/huaweicatalogue`: the
SUN2000 inverter catalogue described first, and the SmartLogger, S-Dongle and
EMMA catalogue described under [Gateway catalogue](#gateway-catalogue).

`profiles/vendor/huawei/catalogue` holds the Huawei SUN2000 inverter catalogue
as generated registry data: every documented model row with its floor, every
read-only and control row of the sixteen profile cards, the value-aligned read
extents, the dictionaries, and the quarantined contradictions. It is generated
by `tools/huaweicatalogue` from reference baseline `2026-10-26.1` of the
consulted CC0 inverter reference, and a byte-for-byte round-trip test checks
it. The facts come from a reference whose original tables, keys and labels are
dedicated under CC0-1.0; vendor publications keep their own rights, and the
catalogue copies no vendor text, link, locator or digest (see
[vendor documentation identity](huawei-vendor-documentation.md)).

Applicability: `evidence.json` lists the consulted source as `huawei-pv-inverter-reference-2026-10-26.1`, the Huawei PV inverter Modbus reference at baseline 2026-10-26.1 of 2026-10-26 (CC0-1.0), cited by title, baseline and date; source pages are carried per row in the catalogue, and no digest is published.

Applicability (gateway catalogue): `evidence.json` names the second consulted source in one applicability line: the Huawei gateway Modbus reference at baseline 2026-10-26.1 of 2026-10-26, dedicated under CC0-1.0, cited by title, baseline and date, with source pages carried per row and no digest. It has no entry under `public_sources`, because that list admits only a publicly addressable locator and the reference has none.

The SUN2000 selection (helianthus-modbusreg issue 362) is the one consumer: it
embeds `editions.json`, `models.json` and the register files, and reads the
card editions, their model rows and the identity rows of each card to decide a
model row from the model text or a recorded wire alias, the model identifier,
the map scope and the row floor (see
[SUN2000 monitoring profiles](huawei-sun2000-monitoring-profiles.md#capability-detection)).
It decodes no register, registers no profile, admits nothing beyond the two
SUN2000 monitoring profiles and grants no write. The monitoring profiles built
on the catalogue are a follow-up.

Companion: the public documentation for this catalogue is merged as
[helianthus-docs-modbus#260](https://github.com/Project-Helianthus/helianthus-docs-modbus/pull/260).

## Inputs

The generator reads the deterministic JSON twin of each of the sixteen cards
and the model table of each of the 49 source editions. Every card has a twin,
so no card falls back to Markdown; a card without a twin stops the generator.
Markdown is read only where the baseline keeps a fact nowhere else: the
edition identity of the source appendix, the card list, core counts and
selection notes of the profile directory, the per-card row counts of the
catalogue navigation, the per-edition model counts, the contradiction
appendix, and the off-grid mode statement of the status chapter.

## Files

| File | Content |
| --- | --- |
| `editions.json` | the reference baseline, the attribution note, and one record per source edition |
| `models.json` | the document-wide requirements and one row per model-table row |
| `registers-<card>.json` | the read-only rows, control rows, read extents, gates and classes of one card |
| `dictionaries.json` | value and status enumerations, bitmaps, sign conventions, sentinels, storage selectors and alarm bits |
| `quarantines.json` | contradictions and anomalies, with the rows that carry each flag |

Every file has a `schema` key (`helianthus-modbusreg-huawei-catalogue-<file>/v1`).
The canonical form puts one top-level key per line and each row of a list on
its own line; decoding and re-encoding a file reproduces its bytes.

## Editions

`reference_baseline` names the baseline (`2026-10-26.1`). Each edition has
`id`, `title`, `issue` (`Issue NN` or `not stated`), `date` (`YYYY-MM-DD` or
`not stated`), `family` and `branch` when the title states them,
`source_class` (`vendor_edition`, or `mirrored_edition` for the MB02 edition,
which came from third-party mirrors), the reference `alias` where one exists,
`card` for the sixteen card editions, and `model_rows`. Distinct editions that
share a title, an issue and a date carry `copy`; distinct titles whose
identifier words coincide carry an `alt` suffix. Only the sidecar tells such
editions apart.

## Model rows

| Field | Rule |
| --- | --- |
| `edition`, `page` | the edition and the physical page of the row |
| `token` | the exact source token, punctuation kept |
| `identifier` | the model identifier where the table labels one |
| `sequence_number` | a table ordinal that the edition does not label as a model identifier; such a row has no identifier and carries M01 |
| `row_minimum` | the minimum the row states, or `not stated` |
| `document_requirement` | the document-wide requirement that applies when the row states no minimum |
| `minimum_software`, `floor_basis` | the floor: the row minimum (`row`) or, when the row states none, the linked requirement (`document`) |
| `wire_aliases` | an alias token with its evidence and scope, only where the reference records one |
| `quarantine` | the identifiers of the quarantines that apply |

`document_requirements` lists each requirement with its edition, page, section,
inclusive minimum, component and model tokens. The floor is the only software
bound. A row states no maximum and no range: what an edition documents applies
from the floor onward, to the builds that follow, until a recorded Helianthus
decision narrows it. Tokens repeat with different identifiers, and a wire
alias holds only within its recorded scope; no punctuation is normalized
globally.

## Register and control rows

Read-only rows carry `key` (the reference's functional key), `endpoint`
(`inverter`, `emma`, `emma-associated-device`; EMMA rows never enter an
inverter read map), `offset` or `address_status` (`unspecified_in_source` for
the two rows whose source address is an ellipsis; they are never requested),
`quantity`, `type`, `access`, `class`, `functional_class`, `gates` (defined in
the file's `gates` list), `condition`, `core` (the card's core key and use gate
for the 429 core rows), `page`, `occurrence` (for a row the source lists twice)
and `quarantine`.

| Rows | Class | Fields |
| --- | --- | --- |
| read-only | `reviewed`, `conditional` | `decode` with the literal `gain` and `unit` cells |
| read-only | `raw-only`, `conflict` | `literal` with the same cells, kept as evidence; never decoded |
| control | `readable-configuration` | `literal` only; an RW row with a documented FC03 read and a documented status, readable as raw evidence |
| control | `no-send` | `literal` only; WO, restricted, conflicting or without a documented read; never requested |

A blank source cell reads `not stated`; `N/A` and other literals stay as
printed. `read_extents` lists the documented value-aligned extents: start, end,
quantity, the quantities that end on a field boundary, the field offsets, the
following source hole and its classification. An extent is no snapshot or
response guarantee, and every row contract still applies. `additive_support`
(MA-C00) carries the identity rows that another edition documents for one
listed model.

## Dictionaries

`id`, `kind` (`status_enum`, `value_enum`, `bitmap`, `sign`, `sentinels`,
`selector`, `alarm_bits`), `card`, `edition`, `endpoint`, `offsets`, `pages`,
`mode_predicate`, `values` (code and meaning), `bits` (alarm words by offset or
by word where the source gives no offset), `modules` where the twin states
them, and `unlisted` (what an unlisted code is). Each dictionary is bound to its
card edition and is never transplanted to another edition.

## Quarantines

`id`, `origin` (`reference` or `generator`), `subject`, `evidence`, `meaning`,
`editions` and `affected` (rows by card, offset, key and occurrence; model rows
by edition, token, identifier and page). The generator flags rows and never
resolves a quarantine.

| Identifiers | Content |
| --- | --- |
| Q01 to Q07 | the quarantined contradictions of the reference, meaning verbatim; Q07 flags only the row the reference names as inconsistent |
| A01 to A08 | the source-specific anomalies (HA and HD string formulas, MB02 35010, PSC110 and optimizer table, MA-V200 32133 to 32137, MC and MA-V200 optimizer table), meaning verbatim |
| M01 | model rows numbered by a sequence ordinal, not a model identifier |
| M02 | row minimums that are merged cells or literals outside the branch form |
| D01 | rows whose enumeration entries the extraction ran together; the row keeps no value dictionary |
| D02 | rows with an enumeration code cut short of a sentinel; a cut code is dropped, a suspected one stays |

## Counts

| Count | Value |
| --- | --- |
| cards | 16 |
| read-only rows | 3115 (372 reviewed, 2127 conditional, 596 raw-only, 20 conflict) |
| control rows | 2135 (1910 readable configuration, 225 no-send) |
| core rows | 429 |
| model rows | 2401 in 49 editions (2282 row floors, 119 document floors) |

The generator also checks each card against the baseline's own accounting: the
validation totals, the per-card row counts, the status counts of every twin,
the core rows per card, the per-edition model counts, the equality of each
card's model table with its edition table, and that every row a twin
quarantines is a conflict or no-send row.

## Regenerating

```bash
go run ./tools/huaweicatalogue -reference <reference root> -sidecar <directory outside the repository>
go run ./tools/huaweicatalogue -reference <reference root> -check
```

The run is deterministic. It stops when a twin or a model table is missing or
inconsistent with the stated accounting, when a string fails the publication
guard, or when the counts differ from 3115, 429, 2135, 2401 and 16; a reviewed
reference change is accepted with
`-expect ro=N,core=N,controls=N,models=N,cards=N`. Locators beyond title,
issue, date and page (source identifiers, digests, table and row positions,
census lines) go only to the `-sidecar` directory, which must lie outside the
repository.

## Tests

`tools/huaweicatalogue` tests the committed files on every run: canonical
round-trip, counts, the class rules (no read-only row decodes beyond its class
and no control row decodes), floors only (row or document floor, never a
maximum), sequence ordinals kept apart from identifiers, token and identifier
uniqueness per edition, the qualification families (identifier 471 resolves to
MC, 428 to MA-C00 and every MAP0 identifier to MA-V200, with the hyphenated
wire alias where the reference records it), unspecified addresses, value-whole
read extents, flag and affected-row agreement, and the publication rules. With
`HELIANTHUS_HUAWEI_REFERENCE` set to the reference root, a further test
regenerates the catalogue twice and compares both runs with the committed
bytes.

## Gateway catalogue

`profiles/vendor/huawei/catalogue/smartlogger-sdongle-emma` holds the
SmartLogger, S-Dongle and EMMA catalogue as generated registry data: eighteen
interface editions with their applicability, every register row of every
endpoint class, the value enumerations and alarm dictionaries, the
quarantines, and the wire services of each edition. It is generated by
`tools/huaweicatalogue -mode gateway` from reference baseline `2026-10-26.1`
of the consulted CC0 gateway reference, through the same schema family,
canonical encoder, validator and publication guard as the inverter part; a
byte-for-byte round-trip test checks it. The directory is named after the
three families because the registry boundary policy refuses ownership
directories named after gateways. Data only: no code reads it (the SUN2000
selection embeds only the inverter files), and the gateway dispositions,
observed cards and fixtures are unchanged.

### Gateway inputs

The generator reads the deterministic JSON twin of each of the eighteen
editions and checks it against the reference index: eighteen editions, 3393
register rows, and the per-edition row, dictionary and alarm-record counts.
Twins are decoded strictly, so a field the generator does not know stops the
run. The twins supply the edition identity, model scope and documented
software minima, every register row with its endpoint, access, cells, row
predicates, inherited endpoint conditions, cell note, quarantine codes and
page, the alarm tuples, narratives and alarm quarantines, and the protocol
facts. Markdown is read only for what the twins lack, each fact parsed from a
table or verified against an anchor sentence:

| Source | Facts taken |
| --- | --- |
| profile card of each edition | namespace table with section start pages (including the forwarded inverter namespace, which has no rows), function list, edition note |
| edition comparison | attribute 6 grammar and descriptor attributes; request object, wrap, exception inventory and list pages are cross-checked against the twins |
| wire chapter | function purposes, functions that are not established, exception meanings |
| discovery chapter | private list objects, attribute dictionary, descriptor grammar |
| connection chapter | query and control spacing, query periods, frame-size statements |
| contradiction appendix | topic table, register type and layout conflict table, alarm collision and dictionary-only tables |

### Gateway files

| File | Content |
| --- | --- |
| `editions.json` | the reference baseline, the attribution note, and one record per interface edition |
| `registers-<edition>.json` | the read-only and control rows and the gates of one edition |
| `dictionaries.json` | value enumerations and the alarm dictionary of each SmartLogger edition |
| `quarantines.json` | the reference topic table, the conflicts and the alarm limits, with the rows, services entries and alarm bits that carry each flag |
| `services.json` | device-list grammar, functions, exception meanings, list objects, attributes, frame limits and one services entry per edition |

The editions, registers, dictionaries and quarantines files use the schema
identifiers of the inverter part; `services.json` adds
`helianthus-modbusreg-huawei-catalogue-services/v1`. Fields added for the
gateway part are optional and absent from the inverter files, whose bytes are
unchanged.

### Gateway editions

Each edition has `id` (family, cover branch where printed, issue number and
date), `title` (family and cover branch; the three SmartLogger editions whose
cover prints no branch carry the family alone), `issue` (`Issue NN`, or `not
stated` where the cover prints its branch in place of an issue), `date`,
`family`, `branch`, `card` (the edition itself), `models` and
`model_list_exhaustive` as the model scope prints them, `floors`, `floor_pages`,
`self_unit` (100 for S-Dongle, 0 for SmartLogger and EMMA), `namespaces`
(endpoint, section start page and row count) and `register_rows`. Each floor
names its `component` (`not stated` where the requirement names none), its
`minimum` and `inclusive: true`: every documented minimum of an edition is an
inclusive floor. No edition states a maximum: what an edition documents
applies from the floor onward, to the builds that follow, until a recorded
Helianthus decision narrows it.

### Gateway register and control rows

| Endpoint | Rows |
| --- | --- |
| `gateway-self` | the gateway's own registers at its self unit |
| `attached-meter` | the attached meter at its own route, with its meter-protocol guard where the source sets one |
| `attached-charger` | the attached charger at its own route |
| `attached-environmental-instrument` | the environmental instrument at its own address |
| `child-alias` | gateway-supplied child-associated aliases |
| `inventory-counter` | the public inventory-change counter 65521, whose route the tables do not establish; it is kept apart from the child aliases |
| `remapped-inverter`, `remapped-environmental-instrument` | offsets in the 25-register block that the remap formula gate of the edition describes |

A row carries `key` (endpoint and offset; signal names are not copied),
`endpoint`, `offset`, `quantity`, `type`, `access`, `class`, `decode` or
`literal` (the gain and unit cells), `gates`, `condition` (the reference's
factual note of the cell, absent where the reference states none), `page`,
`occurrence` and `quarantine`. Each register file also names its edition,
`model_pages` (the requirement pages of the edition), the edition note where
the profile card gives one (`selection_note`) and an empty `read_extents`
list. Gates are defined in the file: the inherited
conditions of each endpoint are `<endpoint>-<n>`, and a row predicate is named
after its kind and value with `kind`, `operator` and `value` fields; the DL/T
645 meter guard is `meter-protocol-dl-t-645` on the forty rows the reference
names.

| Rows | Class | Rule |
| --- | --- | --- |
| read-only | `conflict` | the twin quarantines the row; `literal` only, never decoded |
| read-only | `raw-only` | an opaque multi-register layout without a decode type; `literal` only |
| read-only | `conditional` | a row predicate or a cell note applies; `decode` |
| read-only | `reviewed` | the full tuple with neither; `decode` |
| read-write | `readable-configuration` | `literal` only; readable as raw evidence |
| write-only | `no-send` | `literal` only; never requested |

Every row is documentary: the reference establishes no runtime access or
field-specific write function, and the endpoint conditions always apply.

### Gateway dictionaries

A `value_enum` comes from a cell note whose first sentence is a list of codes
and meanings; it is bound to the reviewed and conditional read-only rows of
its endpoint that carry the note, and withheld from raw-only, conflict and
control rows. Each SmartLogger edition has one `alarm_bits` dictionary: the
tuples (`offset`, `bit`, `alarm_id`, `cause_id`, `label`, `severity`,
`condition`, `page`, `quarantine`) and the `narratives` (`alarm_id`, `label`,
`description`, `impact`, `page`). A bit that carries more than one alarm and
cause pair is a candidate set: each of its tuples carries A01 and none is
selected. A pair printed twice on one bit with two condition texts is one
decode and carries no flag.

### Gateway quarantines

| Identifiers | Content |
| --- | --- |
| T01 to T27 | the topic table of the reference, wording kept apart from source identifiers (replaced by edition labels) and the word for vendor advice (rendered as advisory); bound where the topic names rows or services: the 38000-series remap layout, the environmental remap scope, the Issue 49 serial width, the S-Dongle 37502, 37504 and 37516 presence note (present in all four editions on page 11), the opaque meter identifier, and the routing, frame, zero-count, CRC, Basic-response, Issue 49 and pacing topics on the services entries |
| W01, W02 | the register conflict table rows outside the topics: 40446 to 40458 printed as I64 with two words in the SPC275-container edition (the 40450 width conflict), and 30054 and 30058 printed as U32 with four words in Issue 49 |
| G01 | the attribute 6 grammar, on every services entry |
| A01 to A03 | colliding alarm bits, one alarm printed at two locations, and alarm addresses without a register row |

Every twin row quarantine is bound, and the rows the conflict table names are
exactly the flagged conflict rows. The generator flags and never resolves.

### Gateway services

`services.json` carries the descriptor grammar of the private device list,
the functions (listed, or not established for the file subservices and the
raw and optional functions), the exception meanings with the families that
list each code, the private list objects, the attribute dictionary (1 to 10),
and the frame limits: the standard PDU and TCP ADU limits, the vendor 256-byte
frame claim with its read and write counts, FC03 responses of 9 + 2N bytes,
FC10 requests of 13 + 2N bytes, and the client caps of 123 words for a read and
121 words for a multiple write (255 bytes each), which fit the conservative
gateway arithmetic but guarantee neither block support nor value alignment.
Each services entry gives the self unit, child and reserved unit ranges, unit
notes, byte order, port statement, response timeout, frame limit, read and
write quantities, functions, exception codes and pages, private request
object, wrap beyond FF (no cursor contract), attribute 6 grammar, descriptor
attributes, spacing (required or advisory), query periods and the page range
of each protocol section.

## Rollback

Removing the gateway directory, the `logger_*` files of
`tools/huaweicatalogue`, the gateway section of this page and the gateway
applicability line of `evidence.json`, and reverting the gateway changes to the
shared generator files (`main.go`, `model.go`, `prose.go`, `registers.go`,
`validate.go`), restores the inverter part alone.
Removing the catalogue directory, `tools/huaweicatalogue`, this page, the
README paragraph and the catalogue source and applicability line of
`evidence.json`, and restoring the vendor directory listing in
`huawei_inverter_battery_disposition_test.go`, restores the registry as it was,
once the SUN2000 selection that embeds the catalogue is reverted.
